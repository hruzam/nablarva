## 4. Mismatches discovered

Ranked. Each item: what · why it matters · concrete correction.

**M1 — X1 as written tests a single-client batch executor, not cooperation.** (INFERENCE, from OBSERVED scope)
The operator's request is a shared full terminal with the user (`request.majkee.2026-11-17.md:7`). The proposal
moves every second-client case out of scope (`proposal:59-61`) and keeps only file → shell → result. That is
research family 4 (`research:55`) minus the part that makes it a *shared* terminal. The probe has already
shown same-shell state retention (`probe.py:71-79`). What X1 adds is the receipt and idempotency layer. A
GO on X1 could be read as progress toward a shared terminal while answering none of Oraculum's rows 4–6
(`architecture-preparation:166-167`).
*Correction:* add **one synthetic second client** attached to the same PTY. It can be a fixture attach socket;
a live human is not required. Add an explicit input-owner flag. Then assert that the executor does not dispatch
while the second client holds input. This is the smallest row that turns "batch executor" into "two parties,
one shell".

**M2 — Essential failure condition missing: dispatching into a busy foreground program.** (INFERENCE; Oraculum `:24` names it, the proposal does not test it)
Suppose the shell is running `read`, `less`, `python3` or a pager, whether the human or an earlier request
started it. The executor's next bytes then go to that program, not to bash. A printed sentinel cannot tell you
the shell is back at its prompt. The proposal's negatives (`proposal:67-70`) cover draft, change, duplicate,
stale target and lost receipt, but not this one. This is the failure that matters most for human/agent
cooperation.
*Correction:* add a negative row. A command request submitted while a foreground `read` fixture is waiting
must be **held**, not typed as the answer. Readiness comes from shell-emitted prompt marks (below), never from
screen appearance. Keep only **one request in flight**: write no bytes for request N+1 until request N's
completion is observed.

**M3 — "Restarted executor" conflates executor with PTY owner.** (INFERENCE from probe design)
In the X1 fixture the executor holds the PTY master (`probe.py:43`). When it dies, the master closes and the
shell gets SIGHUP. So a "restarted executor" always means a **new shell incarnation**. That shell does not
retain its state. Tests of restart, stale target and lost receipt therefore exercise fixture behaviour that the
eventual owner (tmux, zellij, the Claude supervisor or a vendor exec) would replace.
*Correction:* state in the launcher that "executor death ⇒ shell death ⇒ new incarnation". Restart tests then
prove only two things: (a) on start, any `dispatched` request without an exit record is reconciled as
`unknown`, with no replay; (b) requests bound to the old incarnation are rejected. Do not claim shell survival
across an executor restart. That needs a separate PTY holder and is exactly the reuse question.
Incarnation = PID namespace + PID + `/proc/<pid>/stat` start time + a nonce the shell prints at start.

**M4 — Completion: three different facts need three different signals.** (SOURCE OSC 133; INFERENCE design)
The proposal correctly limits sentinel claims (`proposal:73-75`) but chooses no mechanism. Recommended fixture
mechanism, which is experiment-local and not a schema:
- The executor writes only a short line, `__tw_run <id>\n`, to the PTY. Request content never travels as PTY
  bytes. This avoids echo, control-character interpretation, bracketed paste and the 4096-char canonical line
  truncation (SOURCE termios(3)). The probe already used this `source <path>` pattern.
- A function preloaded through a private `--rcfile` sources the **executor's approved copy**. It writes `$?` to an
  out-of-band file (`done/<id>.exit` via tmp + rename) = **execution completion**.
- It also emits OSC 133 C/D (and A/B through `PROMPT_COMMAND`) into the stream. These are used only for
  **output slicing and readiness**, i.e. terminal appearance. A screen that shows a prompt is never treated
  as completion.
- Truthful outcomes: exit file present → `exited:<rc>`; shell `waitpid` reports death (for example a request
  containing `exit`) → `shell_ended`; timeout → `unknown`, never "failed, retry".
- Fixture corpus must include harmless shell-hostile cases: `exit`, `set -e`, a request that reads stdin, a
  `trap` change. Sourcing deliberately mutates the shared shell (`architecture-preparation:45-46`), and the
  oracle should show that.

**M5 — Binding content, target and approval while files change.** (INFERENCE)
- *Submit* = atomic rename of a finished draft into `submit/` on the same filesystem, never close/save. Save ≠
  ready is correctly stated at `architecture-preparation:61-65` and SOURCE inotify(7); keep it.
- *Adopt* = the executor copies the bytes into `approved/<id>.sh`, records the sha256 and the target incarnation,
  then checks the hash against the frozen synthetic allowlist (the "approval" for X1). The shell sources only
  that copy, so later edits to the draft cannot change what runs.
- **Same-UID honesty:** the agent fixture can still rewrite `approved/`. Binding is cooperative unless a separate
  UID or similar is used. Label it that way in the evidence, consistent with `proposal:52-54`.
- *Duplicate* is undefined in the proposal. Define it: same request id → no-op that returns existing state.
  Same content with a new id is a **new** request, because deliberately re-running a command is legitimate.
  Write the executor's `dispatched` record **before** the bytes are written (write-ahead). That makes a crash
  between record and write visible as `unknown`.
- *Lost receipt* → the reader queries by id. It never resubmits. The Claude native owner already takes this
  stance (SOURCE `agent-view.md:960`).

**M6 — Three axes must stay three.** (INFERENCE, consistent with Oraculum `:39-52` and arch-prep `:262-270`)
- **Execution scope**: which request hashes may run.
- **Input owner**: who may write bytes now. Use a generation number; a takeover bumps it, and queued agent
  requests stay queued and need re-confirmation after handback, never auto-replay.
- **Lifetime**: detaching a client never ends the shell; kill/recreate is a separate operation.
- **Request kinds**: X1 should implement only `command`, dispatched only at a marked prompt. `input` (literal
  bytes to a named foreground program) should be **rejected** in X1, and the rejection should be tested. That
  keeps "answer the program" from silently becoming "run as shell".

**M7 — Native path is understated: the two vendor facilities cover opposite halves.** (SOURCE + INFERENCE; correction applied)
- `claude --bg --exec 'bash --noprofile --norc'` would plausibly give a supervisor-owned persistent PTY shell
  with documented **human** attach and an agent-readable `claude logs`. The documented agent *input* route is
  only an Agent View TUI reply as typed input (`:222`). There is no scriptable send (`:785-800`), output lives in
  memory only (`:581`), and the jobs directory is not a stable interface (`:829-833`).
- Codex `exec_command`/`write_stdin` is the inverse: agent input/output with no documented human attach
  (`research:23`).
- X1's fixture covers the agent-file half again.
- *Inference:* the missing piece is the same everywhere: **one PTY, two clients, arbitrated input**. That
  strengthens M1. Nothing in current docs closes it natively for either vendor. Running the Claude shell-job
  probe would cheaply confirm or kill the "human half is free" hypothesis. It needs a native-CLI release that X1
  explicitly withholds.

**M8 — Records: JSONL is enough; the proposal is slightly too large here.** (INFERENCE)
- Keep per-request files: `drafts/`, `submit/`, `approved/<id>.sh`, `out/<id>.log` (PTY slice between C and D),
  `done/<id>.exit`.
- Keep one executor-written `events.jsonl` for ordering and audit.
- Drop the current-state snapshot and the Markdown view from X1. Both can be derived and neither is evidence.
- Adopt no schema.

## 5. Recommended next task

**Ranked verdict: 1. REVISE X1** (keep its file → persistent shell → correlated result core), ahead of
2. *prefer the native Claude shell-job qualification* (cheaper for the human half, but it cannot supply agent
input and needs a separate release) and 3. *proceed as written* (it would mostly re-prove the probe and build
idempotency around a fixture owner that the product would not keep).

**Main risk.** X1 passes and is read as a step toward shared terminal cooperation, when it proved a
single-client executor. Its receipt, restart and stale-target machinery would be engineered around a PTY owner
that dies with its executor. The cooperation-critical failure, bytes typed into a busy foreground program,
would stay untested.

**Smallest coherent change.** Rewrite the proposal gate to add exactly two rows and remove two artifacts:
- **+ Row A (second client):** a fixture attach client on the same PTY. It acquires input ownership
  (generation bump). The executor holds every dispatch while that ownership is held. After handback, a queued
  request runs only after re-confirmation. Detaching the client leaves the shell alive.
- **+ Row B (busy foreground):** a command request submitted during a `read` fixture is held, not consumed as
  the answer. It is dispatched only after a shell prompt mark and the out-of-band completion of the previous
  request.
- **− Markdown history and current-state snapshot.**
- **Restate restart as new incarnation** (M3) and **define duplicate** (M5).

Mechanism hints (M4/M5) are offered to the launcher author, not adopted. All of this stays inside X1's
existing effect envelope: stdlib Python, Bash, private `/tmp`, owned PTY, no tmux/zellij server, no native CLI.

**Proposed role for this seat during a released build** (one integration owner = Cartan; independent verifier ≠ author):
- *Preferred:* **parallel reuse lane**, disjoint files. Under its own release, qualify `claude --bg --exec bash`
  against the **same frozen corpus**: human attach/detach, `claude logs` readback fidelity, the absence of
  scripted input, Ctrl-C/EOF via attach, cleanup, and the 5-min output expiry. This produces evidence for the
  "simpler native path" question that X1 cannot produce. Verification goes to Assay or Oraculum, not to me
  or Cartan.
- *Alternative, without that release:* **oracle author before build.** I write the frozen expectations and
  adversarial fixtures (shell-hostile corpus, busy-foreground, mutate-after-submit, duplicate-id, kill-executor)
  before any executor code exists, blind to its implementation. Cartan builds. A third seat verifies. In that
  case I do not also verify, because I authored the oracle the build is judged against.
