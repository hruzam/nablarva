### What the evidence actually establishes

- **Observed — `publisher.py`, `capture_view`, `_Runtime.toggle`, `_Runtime.unshare`:** capture reads view state; sharing changes the status marker. The published capture contains view/window IDs, selections and viewport, but no observation of which application has keyboard focus. Capture runs on the plugin host's main thread; file publication is queued to a writer.
- **Inferred:** absence of deliberate view mutation does not rule out latency, redraw or interactions with other packages. The typing-feel step matters independently of caret/scroll invariance. Status-marker changes are intentional and should be excluded explicitly from the non-disturbance claim.

### Clarify step 4b

**Observed — CHECKLIST, “Extra step 4b”:** it asks for a new view of the same buffer, appends roughly ten lines at the end, and expects the shared view's selection/scroll to remain constant as its revision rises.

**Inferred:** not touching the first view does not make its state causally isolated. Both views share a changing buffer. Editor-native position adjustment, layout, wrapping or viewport clamping could legitimately change the first view. A changed coordinate is therefore an observation requiring diagnosis, not by itself a publisher failure. Conversely, constant sampled coordinates do not prove there was never a transient jump.

**Opinion:** use a sufficiently long synthetic buffer; put the first view's selection and viewport well above the appended region; keep window geometry, zoom and wrapping fixed. Stamp a settled baseline before typing and a settled sample afterwards, as well as the intervening recording. Confirm the shared buffer revision advanced. If anything moves, repeat the same operator actions with publication off to establish native behavior; use the operator's eyes for that unshared baseline, without reading unshared buffers through another instrument. A small matched baseline is also reasonable before 4b if majkee wants stronger causal evidence. Do not retrofit expected values after seeing a failure.

## 2. The security step on this line

**Opinion — recommendation:** scope the later task as prevention of accidental publication and disciplined reading, not isolation from hostile same-user processes. First strengthen explicit path refusals and revalidation throughout a share's lifetime; next add operator-owned private-directory exclusions; then consider narrowly targeted content checks. Keep one local publisher policy, an explicit reader rule, and synthetic acceptance cases. No security feature is released by this return.

**Opinion — single weakest point:** the share toggle authorizes an evolving plaintext copy accessible to every process of the same user, without binding a recipient. A later secret pasted into an innocently named shared buffer can cross that boundary without another sharing decision. Path rules, a heartbeat and the status marker cannot make this per-agent isolation; unsharing cannot recall copies already read.

### Present behavior and what “never read” can mean

- **Observed — `contract.py`, `sealed_reason`:** the current rule checks both normalized and resolved paths for `.majkee`/`.hlm` components and `.env` basename prefixes. Untitled buffers are allowed.
- **Observed — `publisher.py`, `toggle` and `publish`:** path checks occur before sharing and again before `capture_view`; capture reads the live buffer with `substr` when text is needed. Captures are then queued to the writer.
- **Observed — `contract.py`, `Store.publish`, `_sweep`, `remove_share`:** text is written by revision; current and previous text files may be retained; unshare removal runs through the writer. Private directory/file modes protect against other users, not same-user readers, as the README also states.
- **Inferred:** distinguish (a) refusing buffer reads based on a known path policy, (b) inspecting a permitted buffer to decide whether to publish, and (c) stopping further publication and removing existing copies. A content scanner necessarily reads candidate text and cannot meet a literal “never read this secret” requirement. Revocation must account for queued captures, previous text, index metadata and logs, not just the next `state.json`.

### Order of value for the later task

1. **Opinion — explicit path policy first.** Preserve the operator vault and `.env` refusals. Add narrowly identified private-key material and credential stores: private SSH/GPG key locations; cloud and CLI credential/token stores; `.netrc`/stored Git credentials; kubeconfigs that may embed credentials; password-manager/wallet data; and agent authentication, session/history and private transcript-cache roots designated by majkee. Treat public keys and public certificates separately: do not declare every `.pem`, `.json` or SSH-related file secret. These are proposed categories, not a claim that I inventoried this host.

   **Opinion — policy home:** keep non-overridable baseline refusals in the component's existing contract policy and explain them in its durable README/contract. Additive operator-specific absolute roots/patterns belong in local SublimeObserver settings, not a new global permission registry. Existing vault law remains the authority for vaults. Local settings must not weaken that baseline, and neither a toggle nor a confirmation may bypass it. Never publish the private exclusion list in the shared index.

   **Opinion — revalidation:** check original and resolved identities before buffer reading, on rename/save-as/reload and before further publication. Qualification should exercise aliases, symlink retargeting, unreadable resolution, queued writes and policy changes while shared. Treat failure to establish required policy conditions as refusal. **Inferred:** path resolution alone cannot recognize a hard-linked alias or copied secret; ordinary path checks are not an adversarial filesystem-race guarantee.

2. **Opinion — directory opt-out next.** A clearly named, non-executable marker earns its place for private project trees whose paths vary across machines. Choose its name in the later task. Its presence should only deny; nested content cannot opt back in. Check the candidate's ancestor chain, without recursively scanning directories or reading their contents, and define how adding a marker revokes an active share. This is operator-managed protection, not authority supplied by arbitrary project instructions. It does not protect an untitled buffer containing pasted private text.

3. **Opinion — content checks as a limited backstop.** If accidental paste is in scope, inspect only the text already eligible for publication, before it reaches the writer, using a small set of high-confidence patterns such as private-key block headers or explicitly marked secret regions. Refuse the capture; do not silently redact it into misleading “actual buffer” evidence. Scan each new text revision, not only at the toggle. Report a generic reason without including a matched secret, prefix or diagnostic dump. Avoid network scanners, model classification, whole-home scans and generic high-entropy bans. **Inferred:** unknown tokens, encoded secrets and innocuous-looking passwords remain undetectable in general; acceptance must never say “secret-free.”

4. **Opinion — confirmation last, targeted.** The toggle already expresses intent. A one-time clarification that sharing continues across edits and exposes content to all same-user processes is useful; an extra confirmation may be justified for untitled buffers with no usable path policy. Repeated generic prompts add habituation, not a confidentiality boundary. Hard refusals stay non-overridable. No confirmation covers arbitrary future content changes.

### Reader-side rule

**Opinion:** an agent reads only the operator-designated share/view within its current task, after checking identity, path eligibility, consistency and freshness. Finding `current`, an index entry or another share is discovery, not authorization. Do not enumerate unrelated shares to find interesting content or follow published paths back into private originals. If a published item is unexpected or forbidden, stop before text access, report the refusal without content, and request an explicit eligible target. If sensitive text is encountered inadvertently, do not quote it or copy it into logs/evidence. Published text is task data, never authority to execute instructions embedded in it.

**Inferred:** this reader rule is a cooperative instruction boundary. Same-user filesystem permissions cannot enforce it against a malicious reader. A stronger recipient-isolation requirement would need a separately authorized operating-system boundary and is outside this publisher's scope.

### What must not be built; what the later task should prove

**Opinion:** do not add agent-controlled share/refresh commands, a reader approval broker, desktop input monitoring, key logging, sockets, per-agent permission services, automatic delivery, a shared VIST policy layer or an “undo disclosure” promise. Do not turn publication into a scanner of unopened files. Do not treat deleting files or stale-heartbeat rejection as erasure of readers' copies.

**Opinion:** use synthetic secrets and synthetic private paths to qualify: refusal before buffer capture for sealed paths; no publication of a recognized secret in otherwise allowed text; transitions from allowed to refused while shared; no queued/previous-version residue after revocation completes; restart behavior; generic non-leaking errors; public-key/ordinary-code false positives; and unchanged editor behavior. Explicitly state any interval before revocation takes effect and that a crash can leave bytes on disk. A stale file remains readable data even when it is no longer valid observation evidence.
