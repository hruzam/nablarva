## Ranked residual and new findings

### R1 — Major; residual finding 3: revocation has no bound from the operator action

**Observed in source and a supplementary unit probe.** `publisher.py:210–224,343–347`; `contract.py:397–408,451–465,590–623`.

`revoke()` changes only an in-memory set. Existing files and heartbeat remain live until queued removal executes. A heartbeat queued **before** unshare remains authorized; it stamps its execution time, rather than its enqueue time. Consequently it can revive the live-looking revoked capture after a long writer delay. Neither queue length nor filesystem operation duration is bounded by this code. Calling an already-running publish's duration “milliseconds” is a measurement for particular cases, not an implementation guarantee.

Reproduction, using `test_publisher.PluginBase`, `fakes.QueueWriter`, the real Store and a synthetic view in a temporary root:

1. Publish the view and drain the writer.
2. Queue `store.heartbeat`, then toggle unshare. The view is removed from runtime shares immediately; queued removal is behind that heartbeat.
3. Advance the fake clock by 10 seconds, then execute only that prequeued heartbeat.
4. `reader.read_current(root, now=clock.now)` succeeds with the revoked share's original text and identity.
5. Drain removal; normal cleanup then succeeds.

Observed output: `QUEUE PROBE: revoked capture passes fresh live read after 10.0 s`. The delay can be any chosen duration; this is a deterministic scheduling unit probe, not a ten-second real-editor measurement. A long earlier writer task followed by that queued heartbeat supplies the corresponding production interleaving.

Direction: either provide a revocation completion/invalidation boundary that does not depend on ordinary queue service, or explicitly accept completion-based revocation and its lack of a numeric action-to-completion guarantee. The existing three-second wording must not imply a three-second bound from unshare.

### R2 — Minor; a revocation test can erase its own evidence

Changing `Store._is_revoked` to always return false lets queued captures write before removal. ### R3 — Note; external root replacement defeats ownership fencing

**Observed by a supplementary temporary-root unit probe.** `contract.py:241–243,397–413,467–488`.

Start A, externally remove its root, start B at the same pathname, then call A's heartbeat and publish a new share. A and B hold different lock inodes; A overwrites B's publisher header, and both Stores can still successfully publish into the recreated tree. The probe verified both successful publish paths and differing lock inodes. There is no ongoing root/lock identity check before writes. The epoch check at shutdown does not fence these earlier writes; if replacement metadata is absent during startup, old shutdown can also attempt cleanup there before its lock-path check.

This is outside the expressly accepted same-user-interference boundary, so it does not reopen finding 1 inside that boundary. It answers the root-recreation question: the lock is sufficient for cooperating lifecycle operations, not for a directory removed/replaced behind a live holder. Direction: state the boundary; stronger protection would require ongoing ownership/directory fencing.

### R4 — Note; the change adds callback exposure and synchronous path work

**Observed call graph; native-editor exceptions and latency inferred, not demonstrated.** `publisher.py:226–256,268–284,332–337`.

Shared-view edit/selection events now call `file_name()` synchronously before debouncing. An unchanged spelling avoids `realpath`; a changed path or save forces it on the main thread. `file_name()` itself is outside the capture try block, and a poll can reach that call after `_poll_key`'s try block. If that API raises, the new event path propagates it; exceptions thrown inside the resolver are handled by `sealed_reason`. Realpath latency depends on the filesystem, without a timeout. Never-shared events still return after ID checks. There is no observed native-editor failure and no new focus/selection/buffer mutation in the diff.

Direction: retain these as bounded-evidence limits; the new tests do not establish callback fault tolerance or worst-case event latency.

## Ownership interleavings (question 2)

- **Normal unlink race:** source order is sound. Shutdown finishes publication cleanup before unlinking the held lock. A new starter that opened the old inode must compare fd and pathname after flock; ENOENT/mismatch closes it and retries. A starter opening the new inode after unlink may overlap the old holder's fd lifetime, but the old Store has `live=False` and has finished publication writes. The old holder's only remaining filesystem attempt is `rmdir`: a newly named lock makes that fail rather than delete a populated new root. Overlapping held fds on different inodes during shutdown therefore do not alone mean two active publishers.
- **External removal/recreation:** two live writers are reachable, as R3 demonstrates. Removal without recreation leaves `live=True` in the old Store; publish/heartbeat writes fail and log, with no automatic recovery. A new share may create its own directory if someone recreates a usable views tree. Runtime `live` is not a test of current pathname ownership.
- **Bare fork:** the child inherits the open file description and can retain the lock after the parent dies. A new independently opened Store still refuses, potentially indefinitely until every inherited descriptor closes. `O_CLOEXEC` applies at exec, not at fork; fork alone is not a guarantee of kernel release on the original holder's death. No at-fork/pid fencing exists if child code explicitly operates a copied Store. This is not a witnessed automatic second publisher from the plugin runtime, whose writer thread does not survive an ordinary fork into the child.
- **Reload in one process:** independent opens compete even with the same pid. An old load whose unload did not run blocks the new load. Normal unload/stop followed by a new start releases and reacquires ownership. I verified the unit routes, not live Sublime module reload ordering.
- **Start during shutdown:** if flock returns busy, start returns refusal and there is no retry timer. That instance stays nonpublishing until a new runtime/load/start is explicitly performed. The post-lock inode retry does not retry ordinary contention. Rapid directory churn can also exhaust three attempts or fail `_mkdir_private`'s check; Runtime catches ContractError/OSError and refuses. This affects availability, not exclusivity.

## Reader pairing and liveness (question 3)

Under cooperating ownership, unique share IDs, and immutable revision files, **no wrong text/state pairing was found for the complete rule**. A switch cannot redirect a pinned A path into B; missing/swept text causes retry, a changed state identity causes retry, and a different publisher epoch is rejected. A missing text file is an unavailable read, not permission to read a different filename. The reader can return an explicit error/no-text state; that is not a successful text capture.

Even the old two-open `current/...` reader cannot produce the original A-state/B-text pairing with the current writer's share-qualified filenames: B has no `text.<A>.<revision>`. It may fail or obtain an older coherent pair, and it does not establish that current still names that share at completion. Removing the pin alone from the new reader is also covered by its second state check in the tested switch; that redundancy is not permission to simplify the published rule.

Neither pinning nor double-reading creates a lease. `reader.read_current` checks publisher liveness once before resolving and reading the capture. A paused reader may finish after that heartbeat becomes stale or after revocation. Even a coherent state/text pair need not have been read during a fresh-heartbeat interval if the reader paused after its initial check. The durable wording must identify the heartbeat-check instant and the state-consistency interval separately, rather than promise freshness at return. Previously copied bytes cannot be recalled.

## Revocation windows (question 4)

- **From unshare/close:** new and pending captures that have not passed `publish`'s entry check are discarded synchronously. One capture already past that check can finish. Existing text remains readable until deletion, and can pass the live check while queued removal waits. **No finite action-to-removal bound exists.** R1 shows that an old queued heartbeat can refresh the live-looking revoked copy after an arbitrary delay.
- **From a path becoming sealed:** a save callback forces resolution immediately; a changed file-name spelling is checked at the next handled event or changed poll key (nominal poll 500 ms, without a hard scheduler bound). A symlink retargeted under an unchanged spelling while the view is idle does not change the poll key; no forced resolution occurs until save or a later capture. The prior snapshot can remain published and heartbeating indefinitely in that case. This is an existing path-identity limit, not evidence that new sealed text was captured. Path-check exceptions are refused; silent best-effort resolution remains the finding-6 limit.
- **Once removal executes:** a changing current is removed before the index update; the view directory follows. Successful deletion ends new pathname reads, though already-open/copied bytes survive. If removal raises, `_stop_publishing` really sets `live=False`; queued and future Store heartbeats and publishes then become no-ops. If deleting `publisher.json` succeeds, a fresh reader gets NotLive immediately. If current is removed but publisher deletion fails, current-based readers are unavailable immediately; direct view readers still need the heartbeat rule.
- **If all cleanup fails:** residue can remain readable indefinitely, but a newly checking reader rejects it when wall time is **strictly greater than** `last_successful_heartbeat_at + stale_after_s` (the comparison is `>`). Default stale_after_s is 3 s. The bound is from that last successful heartbeat, not from the click or even the start of queued cleanup. Queued heartbeats after the stopped flag cannot extend it. Backward wall-clock changes and readers that checked liveness earlier weaken any real elapsed-time interpretation.

## Other regressions and test sensitivity (questions 5–6)

Shutdown still discards queued work before Store cleanup, serializes against an executing Store operation and releases the fd in a finally block. The writer's two-second join is not an overall shutdown deadline: Store.shutdown subsequently waits for its lock, and filesystem operations themselves have no timeout. This blocking possibility predates step 5. A cleanup failure releases ownership with residue left for stale-heartbeat rejection or next-start cleanup. Stopped publication retains its fd until shutdown, avoiding immediate takeover of its residue.
