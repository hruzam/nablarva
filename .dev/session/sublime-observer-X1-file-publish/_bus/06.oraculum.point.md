## What it is

A Sublime Text package, `SublimeObserver`. When the operator toggles "share" on a view, the
package keeps a file copy of that view's text and state under `/run/user/<uid>/sublime-observer/`
so CLI agents can read it with ordinary file tools. No socket, no control function. Unshared
views must never be published.

## Questions, in order of weight

1. **Can an unshared view's text, path or existence ever reach the runtime directory?**
   Trace every route from an editor event to a file write. Include: events on views that were
   never shared; a share whose view is closed, cloned, moved to another window or reloaded;
   view ids reused by Sublime; the index and `current`.
2. **Can the path refusal be bypassed?** (`sealed_reason`: `.majkee`, `.hlm` components,
   basenames starting `.env`.) Consider symlinks, rename or save-as after sharing, case,
   relative paths, an unresolvable path, untitled buffers.
3. **Can a reader that follows the rule be given a wrong or mixed capture?** The rule:
   `publisher.json` heartbeat younger than the stale bound, then `state.json`, then the text
   file it names. Look at write order, atomic replacement, fsync or its absence, the writer
   queue, revision and seq handling, removal of old text files, truncation at the size cap,
   encoding, and what a reader sees during unshare and shutdown.
4. **After a crash, restart, or a second editor process: is anything stale presented as
   current?** Epoch handling, the one-publisher rule, takeover of a stale pid, cleanup of a
   dead epoch before new content, an unreadable `publisher.json`.
5. **Filesystem safety of the runtime directory.** Modes, ownership checks, symlink or
   pre-created-directory attacks by another process of the same user or of another user,
   `XDG_RUNTIME_DIR` handling, behaviour if the directory is removed while running.
6. **Can the package disturb the editor?** Any call that could change focus, selection,
   scroll, buffer content or settings; work done on the main thread per keystroke and its
   cost on a large buffer; exceptions that could surface as dialogs or break other plugins.
   Is `tests/test_static.py` an adequate guard, and what would slip past it?
7. **Tests.** Which claims above have no test, or a test that would pass on a broken
   implementation? Name the three most valuable missing tests.
8. **Install task.** Any way the install, update or removal block damages another package,
   follows a symlink, or leaves a half-installed state the text does not admit.
