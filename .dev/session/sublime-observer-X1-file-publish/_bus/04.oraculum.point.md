## Where things stand

A Sublime Text package publishes views the operator shares (one toggle per view) as files under
`/run/user/<uid>/sublime-observer/`. It is verified in a disposable Sublime profile and is about
to be witnessed by the operator's hands in his real editor. A read-only recorder logs the
published files during that witness.

## Question 1 — proving the publisher does not disturb the editor

The gate says "focus, selection and scroll are unchanged by publishing". What we have:

- a static test that the package calls no view-changing API (only `set_status` and `erase_status`);
- a disposable-profile trial that compared selection and viewport through the API before and after publishing, with no human input;
- in the real editor: the operator's eyes (checklist step 4), plus one instrumented step (4b):
  the shared view is left alone while the operator types into a second view of the same buffer,
  and the recording must show the shared view's selection and viewport constant while its
  revision rises.

Is there a better way to establish this in a live editor with real input, without querying or
controlling the editor from outside and without adding a control channel? Consider window or
input tracking on KDE Wayland, plugin-side self-checks, or anything else, and say what each
would really prove and what it would cost. Say plainly if the existing evidence is enough.

## Question 2 — a security task on this line

Majkee wants a later step on the ladder for safety: files that must never be read or published
by this mechanism. Today: sharing is one explicit toggle per view; the toggle refuses paths with
a `.majkee` or `.hlm` component and basenames starting `.env`; published files are readable by
every process of the same user; shares do not survive a restart.

Give your view on the scope of such a task, in order of value:

- which paths or contents deserve a refusal the operator cannot trip over by accident
  (key material, credential stores, vaults, others), and where that list should live;
- whether refusal by path is enough, or whether content checks, a per-directory opt-out marker,
  or a confirmation step earn their place;
- what a reader-side rule should be (an agent that finds a published file it was not pointed at);
- what must not be built (anything that turns this observation tool into a controller or a
  shared permission layer);
- the single weakest point of the current trust boundary.
