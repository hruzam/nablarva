## 1. R1 — fixed for delayed queued heartbeats; exact inclusive claim needs correction

**Observed:** `contract.py:388–416`. `revoke()` adds pending synchronously; each heartbeat samples time before checking pending. Independently repeated the original scheduling probe: publish, queue heartbeat, unshare, advance ten seconds, execute only that heartbeat. Its stamp remained `1000.0` at `T=1010.0`; the reader returned `NotLive`.

**Observed:** blocked an actual heartbeat thread at entry to `atomic_write`, after its pending check, then revoked and allowed its write to land ten simulated seconds later. With stamp `1000.0` and `t_r=1000.5`, the reader rejected both at `t_r+3` and after the delayed write. An arbitrarily late file replacement does not make its old timestamp fresh.

**Inferred:** under a common nondecreasing wall clock, while removal is pending, every heartbeat stamp that can land is **at most** `t_r`. It need not be strictly earlier: timestamp resolution can give equal values. Thus the existing reader (`tests/reader.py:35–37`, stale only when age `> S`) guarantees rejection for **T > t_r + S**, not unconditionally for **T ≥ t_r + S**.

**Observed boundary counterexample:** heartbeat passes the pending check with stamp `1000.0`; revoke returns in the same timestamp tick, `t_r=1000.0`; its write lands at `1001.0`; removal remains queued. At `T=1003.0`, `read_current` returns `EQUALITY`; at `1003.001`, it returns `NotLive`. This probe advanced time only forwards. The new in-flight test always advances by 0.5 before revocation (`test_contract.py:659–671`), so it excludes equality. **Opinion: note / contract precision**, not a remaining arbitrary-delay revival.

“Every share” applies while a revocation remains pending. After successful removal, the revoked share is unavailable and other shares may become live again (`contract.py:475–482`; `test_publisher.py:424–445`). It would be false to require unrelated shares to remain NotLive forever after `t_r+S`.

## 2. Can pending stick without removal? — yes, conditionally

**Observed by injected exception; native occurrence unverified:** `publisher.py:210–224`. Unshare pops the runtime share and calls `revoke`, then calls `sublime.status_message` outside a try block **before** submitting removal. If that API raises, no removal is submitted. Close skips that status call; ordinary unshare and path-refusal routes do not.

Probe: publish with QueueWriter, drain, replace only the fake status function with one raising `RuntimeError`, toggle unshare, restore it, advance ten seconds and drain all queued work. Result: pending contains the share, its directory remains, runtime shares are empty, `store.live=True`, `refusal=None`, and the reader returns NotLive. Further polls cannot rediscover the popped share. Heartbeats keep getting skipped until teardown/reload; no stopped-publisher diagnostic is issued.

**Opinion: minor conditional availability defect.** Removal submission should be protected from intervening UI-notification failure. Without such a failure, the ordinary single-main-thread path queues removal in the same call. Successful removal clears pending; removal exceptions deliberately stop publication (`contract.py:465–482,513–523`). A blocked writer/removal can still wait indefinitely by design. No unexpected native failure is established by this fault injection.

## 5. Proposed gate sentence — false without qualifications

**Observed synthetic interleaving; inferred native reachability:** `publisher.py:166–177`; `contract.py:404–416,484–490,622–627`. Stop/reload does not call revoke or set Store.live false before waiting for the writer. Store.shutdown sets it false only after acquiring the same lock that heartbeat holds.

Reproduction: publish; run heartbeat on a thread and pause its clock call after it acquires Store._lock; begin Runtime.stop at wall time `1000`; stop sets active false and reaches writer close/shutdown; advance wall time to `1010`; release the clock call. Heartbeat still sees `live=True` and no pending revocation, writes stamp `1010`, then is paused before releasing the store lock. The complete reader returns `STOP-RESIDUE` at `1010`, while shutdown waits. With the real Writer, its two-second join does not bound that lock wait; the same schedule can extend past it. A process crash at that stage can leave this later-stamped residue until it becomes stale.

This refutes a three-second bound measured from **restart/unload initiation**, not the revocation boundary established for unshare/close. Actual publisher death prevents further user-space heartbeat execution; completed shutdown normally removes the publication. Define which event the sentence means. **Opinion: material wording qualification**, already acknowledged in STATUS, not a newly introduced shutdown regression.

Suggested wording, **opinion**:

> After unshare or close has synchronously revoked a share, a newly checking reader cannot accept that share more than stale_after_s later (3 s by default): its files are removed, or its publisher heartbeat is stale. After actual publisher-process death, the same stale limit applies. Restart/unload initiation alone has no fixed bound while a heartbeat is executing. Removal normally completes sooner, without a deadline.

Named conditions: the reader follows the full epoch/pinning/state/text/state rule and checks liveness at the stated instant; a common nondecreasing wall clock; cooperating ownership without external root replacement; revocation time is callback registration, not the operator's earlier physical action. Equality is accepted by the current reader. Reads that checked earlier and previously copied bytes remain outside this promise. Native smoke and closure documentation remain separate pending work.

**Opinion: sound with named conditions — the R1 mechanism is fixed, but the unqualified inclusive bound, exception-free queueing assumption and restart wording are not established.**
