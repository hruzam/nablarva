# Houston — compact design for Atlas and Oraculum

Houston keeps a project's architectural account usable across sessions and runtimes.
A human or running head invokes it with a bounded question or completed RETURN. It
reconciles enduring facts, exposes contradictions and seeds later work with useful
source pointers. Local cSharps retain initiative. This proposal authorizes no build.

Majkee has blessed the X0 RUNBOOK: **Oraculum owns STATUS/dispatch; Cartan coordinates
design; Atlas challenges and later builds assigned harness artifacts; Trajectory is
mute transport support.** The earlier ownership hold is closed. The RUNBOOK needs the
mechanical corrections in [the handover review](review.cartan.pre-tunnel.2026-10-05.md).
STATUS alone owns the current next action. This file supplies design, not another plan board.

## Shared contract and local method

- Shared identity: purpose, invocation, evidence discipline, one-writer rule, existing
  ownership boundaries, and the difference between observed behavior and a source claim.
- Project addendum: this project's maps, standards, deployment destinations, receipts,
  permitted maintenance target and significant interfaces. It may specialize the method;
  it cannot silently override a lock or confer authority absent from the assignment.
- Native binding: invocation/loading, tool permissions, delegation and runtime settings.
  These can differ between Codex and Claude while preserving the shared contract.
- Output: the existing RETURN plus the smallest warranted documentation change or
  recommendation. No mandatory new report, duplicate journal or whole-session mirror.

Routine authorized moves and edits acquire no Houston approval step. Changes that
break an existing contract or exceed scope still need their actual owner's resolution.
Houston can suggest a new direction; a cSharp turns an accepted seed into a RUNBOOK.

## Concrete process example

A session changes a script's launch contract. Its cSharp names the changed contract,
source revision, deployment target and observed check in its existing RETURN. If that
change affects another component, the responsible owners resolve it under their normal
scope rules. Houston, when invoked, compares that receipt with the project description,
zsh source/deploy documentation and guide references. It proposes or makes an assigned
pointer/description correction, then returns the evidence. A later session starts from
those maintained links rather than rediscovering the old discussion.

The source remains in `ia-sync/zsh`; shared user procedure remains in `reposoma/raw.guides`;
project-specific architecture remains with the project. Houston connects these homes.
It does not copy them into its own vault or deploy changed scripts itself.
