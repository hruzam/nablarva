## The intended relationship

project-specific methods/addenda and native Claude/Codex bindings. Convergence was
provisional; its useful description-maintenance routine can migrate through an explicit
review. Nothing here changes the currently declared maintainer or installs a role.

Majkee asks for **both directions**, with most initiative remaining in the active
session nest. Cartan agrees, with one distinction: Houston should be smaller in daily
activity and wider in view. This is not a command hierarchy expressed as Houston <=
RUNBOOK. Accepted shared contracts bind local work; project narrative and proposals
remain open to contradiction by observed evidence. Majkee retains the gavel.

The aim is that a head can start useful work with less orientation, complete local
work without an architecture ceremony, and return the few findings other heads need.
Houston earns its upkeep by removing repeated research and catching conflicts between
parts. A growing report count is not evidence of value.

## What causes either direction to act

| Trigger | Smallest useful action | Ownership |
|---|---|---|
| Majkee or Houston identifies a useful possibility | A short seed or architecture recommendation with source pointers; the receiving head shapes its gate and RUNBOOK | The session head chooses the work sequence; a proposal alone launches nothing |
| A head starts work inside an established boundary | Read the relevant map/contracts, then proceed under existing authority | No compulsory Houston consultation |
| A planned change affects a shared interface, state home, dependency, placement or deployment promise | Before committing to that change, send the exact proposed difference and affected owners | Houston reconciles the shared consequence; local independent work continues |
| Evidence contradicts the map, or ownership is unclear | Surface the mismatch with its revision/evidence; distinguish outdated docs from implementation drift | The responsible owner resolves routine corrections; consequential locks return to majkee |
| A session produces a lasting architectural result | Reuse its RETURN or closing receipt, promote selected keepers, and link the result into the project account | The head owns the receipt; Houston reconciles what it means across parts |

Reporting is triggered by a meaningful consequence, not every task or every file edit.
When an existing RETURN already states result, source revision, affected contract and
uncertainty, use it. Do not require the head to write a second report, a second journal
entry and a second summary for the same event. A durable promotion can move the existing
receipt to the agreed reports home; an already durable receipt can simply be indexed.

Houston can initiate a bounded review when a specific mismatch appears or majkee asks.
No permanent scan of all scripts, scheduled reporting ritual or new dispatcher is implied.
Routine local work must remain possible while Houston is absent. An unresolved shared
contract still holds its dependent change under the existing ownership/gavel rules.

## Lightest seed for a new nest

An optional `architecture-note.md` is justified only when it saves the new head real
research. Otherwise a short section in the incoming POINT/brief is enough. Four things:

1. The desired outcome and why it matters.
2. The few relevant source/raw pointers, with what remains uncertain.
3. Existing contracts and affected neighbors; distinguish locks from suggestions.
4. The observable result that would settle the question.

The cSharp owns its RUNBOOK and grows the local experiment from there. Houston does
not prescribe substeps, worker choices or the whole folder tree. It may offer competing
interpretations so the nest can investigate instead of inheriting a premature conclusion.
Raw material stays in its current durable home when possible; transfer a scoped pointer
bundle, not every transcript. Valuable raw evidence is promoted explicitly before pruning.

For this conversation, majkee's `(?)` means: give the strongest useful alternative and
creative challenge. It is not a request for automatic agreement or a new global rule.

## Houston's standing content

Keep the purpose/narrative, major component boundaries, interfaces, source and delivery
homes, and the reasons behind consequential decisions discoverable. Track the important
unknowns through their owning documents. Indicate whether a claim is intended, authored,
installed or actually exercised; a source update does not renew a host-behavior receipt.

**Coding standards:** Houston should help reconcile standards with the architecture and
point to their existing owners. Keep concrete rules beside the code or in established
project instructions and formatter/linter/test configuration. Do not maintain a second
Houston copy of those rules. A proposed cross-part convention needs its rationale and
review; Houston's preference alone does not make it a mandatory coding standard.

Other responsibilities worth retaining: notice unowned shared files, expose the cost of
adding a dependency, preserve the reason a design was rejected, and help retire obsolete
interfaces/docs. Name one writer and an order when two sessions touch the same shared file.
Architecture grows through those concrete needs, not a catalogue of every possible duty.

## Durable home

The collection belongs to the project and survives its task sessions. Proposed shape:

```text
docs/ARCHITECTURE.md                  declared public architecture anchor
.dev/project-architecture/
  README.md                         entrance and links to owning documents
  reports/YYYY-MM-DD.<bed>.<milestone>.md
  briefs/YYYY-MM-DD.<topic>.md
  evidence/<topic>/                 selected keepers needing this home
```

Create only what has useful content. `reports/` contains contributed outcomes;
`briefs/` contains Houston's assessments, recommendations and prospective master briefs.
There is no mirrored journal or whole-session tree. Preserve issued receipts; corrections
are linked follow-ups. A commissioned brief names its revision, so later changes do not
silently alter an active head's assignment. Submission is not architectural acceptance.

Supporting maps can split when needed, with one owning document per subject. Existing
research/registry/evidence homes remain valid; link instead of copying them. `README.md`
routes, flag carries settled locks, PROJECT carries its standing contract, and each
RUNBOOK/STATUS pair carries one task's instruction/present state. Do not create another
mutable integration queue inside the collection. Later index/link checks may aid discovery,
but cannot infer semantic acceptance from file presence.

The actual `docs/ARCHITECTURE.md` is currently a pre-architecture pointer. The detailed
candidate remains with architecture session 03 and the working project-design wrapper.
The layout above is a target, not a claim that promotion has happened. Session 03 keeps
its own gate and reviewer; neither Houston design nor this packet closes it.

Before closure/pruning, account for every raw keeper in the promotion manifest and repair
its references. This preserves the RUNBOOK no-session-journal rule and L15's no-archive
rule. `.dev/project-architecture/` has not been created by this proposal.

## Context and transport limits

Persistent streams retain their own reasoning. Exchange the decision/question, source
revision or hash, relevant evidence, write scope and reply path. Freeze a shared candidate
at each review checkpoint; reconcile later feedback against the next revision. Do not
relay entire transcripts through the head. Files carry the accepted contract and recovery.

A spawned agent can sustain interaction if its actual mechanism supports it; spawning
alone neither proves nor denies continuity. Prefer the continuing Atlas session majkee
proposes. Do not assume this exact Cartan chat is already bound: verify the appointed
thread, effective runtime policy, one host-local vault and explicit client release.
A separate appointed build thread is appropriate if this conversation must stay interactive.
The tunnel reaches Codex; it does not give Cartan an outbound door to arbitrary Claude seats.

The protocol keeps one explicit turn order and one lifecycle driver. Source inspection
shows that resume/open/close are not protected like send/ask/steer. Timeout recovery must
reconcile the affected turn and possible partial effects before continuing. The supplied
probe supports a verified short reply with timeout 600 configured; it does not establish
600 seconds of sustained work or reliable contention between two callers. No live tunnel
experiment was run in this sitting, and transport defects remain with that owner.
