# G10 — a vendor-neutral "friendly reminder" when a seat is asleep

**Why:** an open cycle looks the same whether the seat is working, stuck on a dialog, out of context or gone. Today the waiting
owner checks by hand. Majkee asked for a small, vendor-neutral helper with a timer.

**The shared chapter already describes the sober form.** file-poke says: the waiting owner owns reconciliation; a finite check-in
names its read scope, threshold, output, expiry or maximum count and responsible seat; a file-only note may flag an aged unanswered
POINT or an unreviewed RETURN; it must account for STOP and BLOCKED; it must not infer health from silence or file age; no empty
reminders, no redispatch; automatic sends need their own authority. Stage 1 is that check-in as a script, nothing more.

**Two stages, on purpose**

- **Stage 1 — one owner-side deadline check of a numbered cycle.** Given a bed and a cycle number it reads the cycle's files and
  prints one outcome: closed by a VERDICT (including STOP or BLOCKED without a RETURN) · a complete RETURN waits for review · the
  obligation was still outstanding at the check. It writes at most a file-only note. It types into no pane, not even the owner's:
  pane input is an actuator action (L20), and a desktop notification is a separate output channel that Majkee would have to name.
- **Stage 2 — one reminder to the silent seat.** A second send through that seat's door. It is delivery (L21). After an uncertain
  first send it is forbidden until the receipt is reconciled.

**What a timeout means:** only that the obligation was outstanding when checked. It says nothing about the seat's health.

**Parts that already exist (nothing vendor-specific)**

- tmux `monitor-silence <seconds>` flags a window that printed nothing for that long. No script. Setting it is Majkee's hand.
- A one-shot timer: `systemd-run --user --on-active=<time>`; a deadline: `timeout` with a poll loop.
- Ancestor in the archive: `vist-heartbeat.py` — one bounded wake under a lease (expiry, max wakes, pending id). Evidence, not a
  live tool; its guards are the right ones to copy.

**Edge cases the design must answer**

1. Busy is not asleep: silence proves nothing, so the check reports files, not health.
2. The first poke was uncertain: no reminder at all until the receipt is reconciled. A "harmless repeat" does not resolve uncertainty.
3. The cycle was closed by STOP or BLOCKED without a RETURN: a watcher that only looks for the RETURN path would call that seat late.
4. The seat is gone: panes are shell-rooted, so stage 2 must look first or not send.
5. A dialog is on screen: Enter would answer it. Stage 2 never sends into a dialog.
6. The RETURN exists but is half written: check for the last heading, not for the file.
7. Two checks on one cycle: one lock file per cycle. The check is finite and leaves a line when it ends.
8. Count: at most one reminder per cycle in stage 2, then the human is told.

**Done when (stage 1):** one script under about 60 lines, no daemon, with the lock, the completeness check and the three outcomes;
tried on one real cycle of the bed that builds it; read by a non-author. **Stage 2** is only specified here, not built.

**Bounds:** no daemon, no cron, no resolver, no envelope, no generic launcher. The script changes no tmux option and types nothing.

**Open questions:** where the script lives (bed-local, or the session-window line in ia-sync); whether Majkee wants a second output
channel beyond the printed line and the file note.
