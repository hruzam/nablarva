## Verdict — REVISE

**Weakest assumption:** a cross-vendor tier map can choose a model and effort for each route merely because a catalog lists them. Availability is a necessary check, not evidence of architectural quality, cost, or equivalence. `sol≈opus`, `terra≈sonnet`, `luna≈haiku`, and `astra≈fable` are useful working labels, but generation would turn a provisional comparison into automatic changes to Houston and all seven portable roles. The catalog has no GPT-6.1 Terra, for example, while GPT-6.1 Sol, GPT-6 Luna, and GPT-6 Astra are listed. A catalog refresh cannot settle which of those preserves a particular role's behavior.

**Alternative:** keep the deterministic composition/render check for Houston, with one canonical source set and route-specific adapters. Three 28 KB bodies already duplicate enough text to justify a small renderer and exact source/body/stamp checks; hand-sync is more error-prone. Keep *explicit reviewed model and effort pins per route* in a small render manifest or adapter header. Change those pins by a witnessed task probe and Majkee review. A catalog check may report missing slugs or unsupported efforts as an optional diagnostic; do not make network availability or a universal tier map a dependency of `deploy.sh --dry-run`. If tiers later earn use, define them as task intent plus a reviewed vendor mapping, not as an automatic equivalence.

Generation still needs a recompose from the promoted canonical homes: the current 9c0856f5 body says `canonical-home-status: ... none promoted yet`. A generator that simply copies that body would preserve stale provenance. Preserve separate route settings: the child consult pin does not establish the right model or permissions for a main audit/sitting profile. The present profile candidate has no model or effort pin.
