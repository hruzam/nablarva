## Verdict on the architecture seam: CONFIRM the split, REVISE the carrier mapping

Cartan's split into **consultation** (a waiting Claude call returns a Codex answer) and
**living-peer exchange** (two already-running sessions, native UI and approvals, qualified
return wake) holds, and the source supports it. The tunnel shim starts or resumes *its own*
stored thread through a per-call `codex app-server --stdio`. It never addresses an
already-running interactive Codex seat, and it replaces approvals with
`approvalPolicy: never` plus auto-decline. So it cannot stand in for the living-peer gate.

The revision: **the note maps "a planner asking for a second opinion" onto the tunnel. The
tunnel's own guide maps that need elsewhere.** `raw.guides/tunnel/GUIDE.md:17-24` routes
multi-turn continuity work to the tunnel, a one-shot blind second opinion to `@vega`, and a
one-shot adversarial audit to `@mirror`. Both relays use
`ia-sync/zsh/ai/codex-run.zsh` (`codex exec --json --ephemeral`, :37). There are therefore
**two consultation carriers**, not one:

| | tunnel (`tunnel-codex.zsh`) | one-shot relay (`codex-run.zsh`) |
|---|---|---|
| Context | stored thread; remembers across calls | ephemeral; fresh every call |
| Operator gate | `open --enable` required (Law 2.4) | none beyond the calling seat's permissions |
| Default sandbox | `read-only` (py:325-326, zsh:176) | `workspace-write` (codex-run.zsh:37) |
| Wait limit | 120 s per wait, `TUNNEL_CODEX_TIMEOUT` (py:115) | 300 s, `CODEX_TIMEOUT` (codex-run.zsh:20) |
| Input | one argv string | argv or stdin (`-`), but passed on as argv (:37) |
| Reply check | `ask` compares streamed text with read-back (exit 50) | `jq` extraction of the final agent message plus usage tail |

A second opinion's value is decorrelation. A stored thread accumulates its own earlier answers,
so its independence decays from ticket to ticket. The note says so itself (:14-15: "not
necessarily a fresh, context-free opinion"), but it still names the tunnel as the carrier for
the second-opinion use. **Proposed amendment:** "consultation" names a capability with two
existing carriers. The default for a planner's second opinion is the ephemeral relay; the
tunnel is for continuity consultation (a follow-up that needs the earlier turns). Neither
needs a new bus, daemon or reverse wake.

## 4. Mismatches discovered

- **M1: Carrier mapping (see verdict).** The note routes the second-opinion use to the
  tunnel; `GUIDE.md:17-24` routes it to `@vega`/`@mirror` → `codex-run.zsh`. Also, the
  one-shot relay runs `--sandbox workspace-write` (codex-run.zsh:37), which is more
  write-capable than the tunnel's read-only default, for a task that is only meant to read.
  I am naming this, not fixing it; it belongs to ia-sync.
- **M2: The receipt does not cover `ask`.** `t06-tunnel-v0-roundtrip.md` contains no
  occurrence of `ask`. Re-run 2 was driven by `send` (:183). `ask` arrived afterwards in
  `5a0a59f` (09-03 15:24). The field evidence for `ask` is the dev journal (09-04, 09-10),
  not a PASS receipt. The note's pairing of `cmd_ask` with "the dated round-trip receipt"
  overstates what the receipt proves.
- **M3: Version drift.** Installed codex resolves to **0.158.0**. The shim's protocol pin is
  0.152.1 (py:7), and the upgrade card targets 0.154.0. The app-server protocol is labelled
  experimental (py:7-9). The note correctly makes no compatibility claim; this puts a number
  on the gap: six minor releases beyond the last proof.
- **M4: The 120 s limit is the working ceiling for consultation.** `DEFAULT_TIMEOUT` = 120 s
  (py:115) applies to each wait separately. A timeout raises `ProtocolError`; the `finally`
  block then closes the transport, and per the journal (09-04 #1, 09-10) killing the driver
  **interrupts the server-side turn** (`status: interrupted`, no final answer). Research-grade
  consultations (reading many files, web search) exceed 120 s. The note's "waiting call"
  framing needs this bound stated. The observation's "6.025 s" is almost certainly the time
  *remaining* on the 120 s deadline, not a 6 s window (py:369-372). That is my reading, not
  a reproduction.
- **M5: Handle loss is concentrated on thread birth, and a field observation fits it.** In
  `cmd_ask` a new `threadId` lives only in memory (py:641) until `save_state` at :656, after
  `drive_turn` and `reconcile`. Any exception in between loses the handle of a thread that
  already exists on the server. On *resume* the threadId is already saved and only
  `lastTurnId` is lost. Once the turn completes, a mismatch (exit 50) still saves first (:655
  before :658), which is good. The 09-10 observation (:9-12) fits this: a cold `ask` timed
  out, state still showed `threadId: null`, and the next `send` "born" a thread, which on
  this reading was a second thread. The source does not show whether the orphaned first
  thread was ever recorded. Not reproduced here.
- **M6: The exit-code contract and the observation disagree.** In source, a timeout →
  `ProtocolError` → exit 30 (py:100, :250, :745; the zsh `exec` passes it through, :264).
  The 09-10 observation records **exit 0** twice, and the journal calls this a "contract
  defect". The shim source has not changed since 09-03, so either the observation captured
  the exit status wrongly (for example, through a pipe), or something outside the shim
  masked it. I cannot resolve this without a live probe. Until it is resolved, a ticket
  consumer must not treat exit 0 alone as proof of a delivered answer. It should also check
  that the stdout tail is present, or use `read`.
- **M7: Input handling a file-backed ticket will hit.** zsh:209 takes only `positional[1]`,
  so **extra unquoted words are silently dropped** (`tun ask hello world` sends `hello`).
  There is no file or stdin input. A prompt file must go in as one argv string, which Linux
  caps at 128 KiB per argument (MAX_ARG_STRLEN; general kernel fact, not checked on this
  host). `codex-run` accepts stdin but also passes it on as argv (:37), so it has the same
  cap.
- **M8: STATUS vs card (confirming the note, preserved, not repaired).** STATUS
  frontmatter says "No T-task started yet" while its table says T1 "DONE … Uncommitted". The
  card says T1 is "done, committed, verified present on disk" at `5af457f` (a commit that
  exists). STATUS was last committed in `d8df3e5`, still with those words. The owner is
  Trajectory, in ia-sync.
- **M9: Stale shim header (confirming the note).** zsh:14 says "NOT deployed", while the
  live copy matches source byte for byte. The `tun` alias is defined at
  `ia-sync/zsh/ai/keyboard.zsh:221`; whether it resolves in a live shell was not checked, and
  the journal (09-04 #8) warns that it may not resolve in a non-interactive shell.
