# @Epoch s02 — Codex CLI self-display, DOCUMENTED (2026-11-26, all live-fetched today)

Doc host note: developers.openai.com/codex/* now 308-redirects to learn.chatgpt.com/docs/*. Pages carry no date; "page date" below = fetched 2026-11-26, undated by the vendor.

**1. Native display, nothing typed.** The docs do not describe header or footer layout in prose. The one documented default: footer status line = `model-with-reasoning`, `context-remaining`, `current-dir` (config-sample comment). `/status` shows chat ID, context usage, rate limits (slash-commands reference) and "active model, approval policy, writable roots, token usage" (developer-commands). Header/banner contents: not documented.

**2. Configurable: yes.** `tui.status_line` = ordered array of item IDs; unset uses the default above; `[]` hides the footer (sample) and `null` disables it (reference). `/statusline` picks and reorders items interactively and persists to `tui.status_line`. `tui.terminal_title` = ordered IDs, default `["spinner","project"]`; the sample lists `app-name, project, spinner, status, thread, git-branch, model, task-progress`; `/title` edits it. The /statusline page names the footer items in prose only: model, model+reasoning, context stats, rate limits, git branch, token counters, session id, current dir/project root, Codex version. The exact status_line ID strings are NOT enumerated in official docs (sample shows only `model`, `model-with-reasoning`, `context-remaining`, `current-dir`, `git-branch`). Multiline: not documented. Overflow/truncation of wide text: not documented. No custom-command status line is documented (a search-result claim that it is a fixed enum is third-party, L).

**3. Data-receiving programs.**
- `notify = [argv...]` (top-level): runs on `agent-turn-complete` only; one JSON argument with `type`, `thread-id` ("session identifier"), `turn-id`, `cwd`, `input-messages`, `last-assistant-message`. No model, effort or context.
- Hooks (`features.hooks`; inline `[hooks]` or hooks.json): command hooks get JSON on stdin with `session_id`, `transcript_path` (string|null), `cwd`, `hook_event_name`, `model`. Events: PreModelRequest, PostModelRequest, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SessionStart, SessionEnd, SubagentStart, SubagentStop, UserPromptSubmit, Stop, Interrupt. Per-event extras: SessionStart `source`; Stop/UserPromptSubmit `turn_id`, plus `last_assistant_message` / `prompt`. Output `systemMessage` is "surfaced as a warning in the UI"; hook `statusMessage` is shown while an MCP tool hook runs. Hooks cannot be shown to feed the status line (not documented).
- `tui.notifications` / `notification_method` (auto|osc9|bel) / `notification_condition` (unfocused|always): built-in terminal alerts; filter example `["agent-turn-complete","approval-requested"]`.

**4. Clock/timers:** no clock item and no timer item documented in the status line or title lists (title has `spinner`, `status`, `task-progress`). Alerts: see notifications above.

**5. Release notes.** Only 0.172.0 (24 Nov 2026, Latest at fetch) is relevant: "Expose custom status lines in `/experimental`" (#62387) — meaning of "custom" and whether this is the same as `tui.status_line` is NOT explained in the notes (open). Also #62202 omits unknown server versions from `/status`. No footer, hook, notify or title change in 0.172.0. 0.165–0.171 and 0.173+ stable notes not seen (0.173/0.174 appear only as alpha). The config reference page claims `tui.status_line` and hooks without a "since" version.

**Gaps / caveats.** Official docs never state: wrap/truncate behaviour, multiline, full item enum, whether `/experimental` custom status lines are a different mechanism. Do not assume; these need observation (outside this task).
