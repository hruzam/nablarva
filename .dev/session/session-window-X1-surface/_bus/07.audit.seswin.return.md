1. **The custom footer can receive data.** Correct field-list lines 33–36 and 54–56. `tui.status_line` selects built-in items. If it exceeds the available columns and has multiple rows, Codex wraps it. With one row available, or more content than the allotted rows can hold, the renderer truncates with an ellipsis. The composer shares a budget of up to four rows with hints. The upstream 18-column test expects four or three status rows in fullscreen, two or one inline, depending on the mode indicator. **Inference for point 7:** wrapping explains the lead’s report. `profile` goes through the ordinary segment loop. There is no dedicated profile row. At the same height and with the same items, enough extra width should bring it back onto the preceding row. This is a prediction for the width check. 4. **Freshness depends on the value.** Correct lines 13–17, 35 and 55. The native footer recomputes on events including selection changes, thread renames, turn transitions, completed Git lookups and rate-limit reports. Context reflects the latest token report. An idle native footer can retain its last value until the corresponding source updates. There is no single clock interval for all items. Some inputs have their own schedule, including eligible rate-limit polling (60, 30, 15 or 5 seconds according to consumption) and the selected workspace headline (five minutes when eligible). The selected MCP provider takes a fresh snapshot per read, allows one second for the resource reply, then waits one second **after success** before the next read, including while idle. An error or timeout stops the loop. A fresh read can still contain an unchanged token report.
